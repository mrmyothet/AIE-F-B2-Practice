## 1. Purpose and Scope

This document defines how the prototype is built: the system shape, the layers, the
data flows that matter, and the complete database schema with its Row Level Security
policies and triggers.

It covers the MVP defined in PRD §51. Everything in PRD §49 (Non-Goals) is explicitly
out of scope, including real GPS hardware, microservices, and route optimisation.

## 2. System Context

There is no custom backend server. The Next.js application talks directly to Supabase,
and Supabase *is* the backend.

```text
┌──────────────────────────────────────────────────────┐
│  Browser — Admin / Trader / Driver                   │
│                                                      │
│  Next.js App Router + React + TypeScript + Tailwind  │
│  ├─ Server Components  → initial data fetch          │
│  ├─ Client Components  → realtime, Leaflet, forms    │
│  ├─ middleware.ts      → role-based route redirects  │
│  └─ localStorage queue → driver offline updates      │
└───────────────┬──────────────────────────────────────┘
                │
       HTTPS (PostgREST)          WSS (Realtime)
                │
┌───────────────▼──────────────────────────────────────┐
│  Supabase                                            │
│  ├─ Auth      — JWT sessions in cookies              │
│  ├─ Postgres  — 6 tables + RLS + triggers            │
│  ├─ Realtime  — WAL → websocket broadcast            │
│  └─ Storage   — shipment-documents bucket            │
└──────────────────────────────────────────────────────┘

Hosting: Vercel        Map tiles: OpenStreetMap (no API key)
```

### The consequence of this shape

The browser holds a real database credential (the Supabase anon key plus the user's JWT).
There is no API layer that all traffic must pass through, so there is nowhere to put a
single `if (role !== 'ADMIN') return 403` check.

> **Row Level Security is the actual access control. Hiding buttons in React is cosmetic.**

PRD §8 ("users must not access another role's function by typing a URL") is satisfied by
middleware. PRD §35 ("traders can only manage their own shipments") is satisfied **only**
by RLS. Both are implemented, and they are independent of each other by design.

## 3. Architectural Decisions

| # | Decision | Rationale | Trade-off accepted |
|---|---|---|---|
| 1 | Backend-as-a-Service instead of a custom API server | Three-day build window; removes an entire deployment target and its auth plumbing | Business logic lives in SQL triggers rather than an application service layer |
| 2 | Authorisation in Postgres RLS, not in application code | With a direct-to-database client there is no other chokepoint | Policies are harder to unit-test than TypeScript guards; must be verified manually with two browser sessions |
| 3 | Route-closure alerts generated by a database trigger | Atomic, and fires even if the admin closes the browser mid-operation | Logic is in PL/pgSQL, which the team must read as carefully as TypeScript |
| 4 | Client-generated UUIDs for `shipment_events` | Makes offline replay idempotent — a retried sync cannot duplicate timeline entries | Client controls a primary key; acceptable because RLS still validates the row |
| 5 | Simulated GPS via route waypoints stored in the database | PRD §18; no hardware, no billing account, deterministic demo | Not real tracking — must be labelled as simulated in the UI |
| 6 | Leaflet + OpenStreetMap over Google Maps / Mapbox | No API key, no credit card, no quota risk before a deadline | Fewer features; tile server is best-effort |
| 7 | `localStorage` for the offline queue, IndexedDB only for photo blobs | Zero dependencies and inspectable live in DevTools during the demo | ~5 MB quota; JSON only |

**Why the service layer is mandatory:** the code is AI-generated. When the model emits a

of twenty components.

## 5. Key Data Flows

### 5.1 Real-time GPS update

```text
Driver taps "Update Location"
  → waypoint_index + 1, look up next waypoint from routes.waypoints
  → shipmentService.updateLocation()  →  UPDATE public.shipments
  → Postgres commits, writes WAL entry
  → Realtime server reads WAL, re-checks RLS per subscriber
  → pushes over websocket to Admin and Trader sessions
  → React state updates → Leaflet marker moves, no page refresh
```

Satisfies PRD §54 "Realtime: location changes appear without manual refresh".

### 5.2 Route closure → alert fan-out

```text
Admin toggles Muse route OPEN → CLOSED
  → UPDATE public.routes SET status = 'CLOSED'
  → trigger trg_route_status_change fires inside the same transaction
      ├─ finds every non-delivered shipment on that route
      ├─ inserts one alert per trader and per driver
      ├─ sets qualifying shipments to DELAYED
      └─ writes a DELAYED shipment_event so the timeline stays truthful
  → Realtime pushes the new alerts to their recipients only (RLS-filtered)
  → Trader and Driver see the alert without refreshing
```

The alternative — looping in the admin's browser after the update — is non-atomic: a
closed tab mid-loop leaves some traders unalerted. The trigger also demos better, because
it shows the database itself reacting.

### 5.3 Driver offline queue

```text
Driver action → queueOrSend()
   online?  → write to Supabase immediately
   offline? → push { id: crypto.randomUUID(), type, payload, ts } to localStorage
              → OfflineIndicator renders  🔴 Offline · Pending: 2

window 'online' event  (or manual "Sync Updates")
   → replay queue in timestamp order
   → INSERT ... ON CONFLICT (id) DO NOTHING
   → clear queue → 🟢 Online · 2 synchronized
```

Two rules that make this survive questioning:

1. **Every** driver write goes through `queueOrSend()`. If any write bypasses it, offline
   mode works for the happy path and breaks under scrutiny.
2. The client-generated UUID is the idempotency key. Without it, a retried sync duplicates
   timeline events.

**Photo uploads offline:** base64 images will exceed the `localStorage` quota. Blobs are
queued in IndexedDB and uploaded on reconnect. PRD §25 and the brief both permit this
being *proposed* rather than fully built — say which one you did.

## 6. Authentication and RBAC

```text
signInWithPassword
  → Supabase Auth issues JWT, @supabase/ssr stores it in cookies
  → middleware.ts reads the session, loads profiles.role
  → redirect  ADMIN → /admin   TRADER → /trader   DRIVER → /driver
  → every subsequent query is independently re-checked by RLS
```

`profiles.id` is a foreign key to `auth.users.id`, populated by an `AFTER INSERT` trigger
on `auth.users` (§10.1).

**Avoiding infinite RLS recursion.** A policy on `shipments` that sub-queries `profiles`
will recurse, because `profiles` has RLS of its own. The role lookup is therefore wrapped
in the `SECURITY DEFINER` functions `public.is_admin()` and `public.current_role()`, which
bypass RLS on `profiles`. This is the single most common failure mode in AI-generated
Supabase policies — it produces a `stack depth limit exceeded` error that looks unrelated
to the policy that caused it.

### 8.2 Helper functions

Defined before the policies because every policy depends on them.

```sql
-- SECURITY DEFINER: bypasses RLS on profiles, which is what prevents
-- policy recursion when other tables need to know the caller's role.
create or replace function public.current_role()
returns public.user_role
language sql
stable
security definer
set search_path = public
as $$
  select role from public.profiles where id = auth.uid();
$$;

create or replace function public.is_admin()
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1 from public.profiles
    where id = auth.uid() and role = 'ADMIN'
  );
$$;

grant execute on function public.current_role() to authenticated;
grant execute on function public.is_admin()     to authenticated;
```

## 9. Row Level Security Policies

```sql
alter table public.profiles        enable row level security;
alter table public.routes          enable row level security;
alter table public.shipments       enable row level security;
alter table public.shipment_events enable row level security;
alter table public.alerts          enable row level security;
alter table public.documents       enable row level security;
```

RLS is deny-by-default: with it enabled and no policy, every query returns zero rows.
Each policy below re-states one line of the permission matrix in PRD §6.

### 9.1 `profiles`

```sql
-- Read: yourself; admins read everyone; any driver is readable so traders can
-- populate the "assign driver" dropdown; plus your counterparty on a shared shipment.
create policy "profiles_select"
  on public.profiles for select to authenticated
  using (
    id = auth.uid()
    or public.is_admin()
    or role = 'DRIVER'
    or exists (
      select 1 from public.shipments s
      where (s.trader_id = profiles.id and s.driver_id = auth.uid())
         or (s.driver_id = profiles.id and s.trader_id = auth.uid())
    )
  );

create policy "profiles_update_self"
  on public.profiles for update to authenticated
  using      (id = auth.uid() or public.is_admin())
  with check (id = auth.uid() or public.is_admin());
```

> `role = 'DRIVER'` is a deliberate prototype shortcut: it exposes driver names and emails
> to any signed-in user. In production the driver picker would read from a view that
> exposes only `id` and `name`.

A user may update their own profile, so they could otherwise set their own
`role = 'ADMIN'`. That is blocked in §10.3.

### 9.2 `routes`

```sql
create policy "routes_select_all"
  on public.routes for select to authenticated
  using (true);

create policy "routes_admin_write"
  on public.routes for all to authenticated
  using      (public.is_admin())
  with check (public.is_admin());
```

### 9.3 `shipments`

```sql
create policy "shipments_select"
  on public.shipments for select to authenticated
  using (
    public.is_admin()
    or trader_id = auth.uid()
    or driver_id = auth.uid()
  );

-- Traders create shipments for themselves only; admins may create any.
create policy "shipments_insert"
  on public.shipments for insert to authenticated
  with check (
    public.is_admin()
    or (trader_id = auth.uid() and public.current_role() = 'TRADER')
  );

-- Traders cannot update shipments at all (PRD §6). Drivers may update only
-- shipments assigned to them; the columns they may touch are limited in §10.4.
create policy "shipments_update"
  on public.shipments for update to authenticated
  using      (public.is_admin() or driver_id = auth.uid())
  with check (public.is_admin() or driver_id = auth.uid());

create policy "shipments_delete_admin"
  on public.shipments for delete to authenticated
  using (public.is_admin());
```

### 9.4 `shipment_events`

The `exists` sub-query runs under the caller's own permissions, so `shipments_select`
transitively restricts which timelines are visible. No role logic is duplicated here.

```sql
create policy "shipment_events_select"
  on public.shipment_events for select to authenticated
  using (
    exists (select 1 from public.shipments s where s.id = shipment_id)
  );

create policy "shipment_events_insert"
  on public.shipment_events for insert to authenticated
  with check (
    created_by = auth.uid()
    and exists (
      select 1 from public.shipments s
      where s.id = shipment_id
        and (public.is_admin() or s.driver_id = auth.uid())
    )
  );
```

### 9.5 `alerts`

Recipients read their own alerts and may mark them read. Inserts are admin-only; the
route-closure trigger is `SECURITY DEFINER`, so it inserts regardless of this policy.

```sql
create policy "alerts_select_own"
  on public.alerts for select to authenticated
  using (recipient_id = auth.uid() or public.is_admin());

create policy "alerts_update_own"
  on public.alerts for update to authenticated
  using      (recipient_id = auth.uid())
  with check (recipient_id = auth.uid());

create policy "alerts_insert_admin"
  on public.alerts for insert to authenticated
  with check (public.is_admin());
```

### 9.6 `documents`

```sql
create policy "documents_select"
  on public.documents for select to authenticated
  using (
    exists (select 1 from public.shipments s where s.id = shipment_id)
  );

create policy "documents_insert"
  on public.documents for insert to authenticated
  with check (
    driver_id = auth.uid()
    and exists (
      select 1 from public.shipments s
      where s.id = shipment_id and s.driver_id = auth.uid()
    )
  );
```

## 10. Triggers and Automation

### 10.1 Create a profile for every new auth user

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  insert into public.profiles (id, name, email, role)
  values (
    new.id,
    coalesce(new.raw_user_meta_data ->> 'name', split_part(new.email, '@', 1)),
    new.email,
    coalesce((new.raw_user_meta_data ->> 'role')::public.user_role, 'TRADER')
  );
  return new;
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

> **Prototype-only shortcut.** Reading `role` from user metadata means anyone who can sign
> up could claim `ADMIN`. Acceptable here because the six demo accounts are created from
> the Supabase dashboard and public sign-up is disabled. In production the default would be
> `TRADER` unconditionally, with promotion done by an existing admin.

### 10.2 Maintain `updated_at`

```sql
create or replace function public.touch_updated_at()
returns trigger language plpgsql as $$
begin
  new.updated_at := now();
  return new;
end;
$$;

create trigger trg_shipments_touch
  before update on public.shipments
  for each row execute function public.touch_updated_at();

create trigger trg_routes_touch
  before update on public.routes
  for each row execute function public.touch_updated_at();
```

### 10.3 Block role escalation

```sql
create or replace function public.prevent_role_escalation()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  if new.role is distinct from old.role and not public.is_admin() then
    raise exception 'Only an administrator may change a user role';
  end if;
  return new;
end;
$$;

create trigger trg_profiles_role_guard
  before update on public.profiles
  for each row execute function public.prevent_role_escalation();
```

### 10.4 Restrict which columns a driver may update

RLS grants or denies a whole row; it cannot limit columns, and Postgres column-level
`GRANT`s cannot help because admins, traders and drivers all share the single
`authenticated` database role. A trigger is the correct mechanism.

```sql
create or replace function public.enforce_driver_update_scope()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
  if public.current_role() = 'DRIVER' then
    if new.tracking_number   is distinct from old.tracking_number
    or new.trader_id         is distinct from old.trader_id
    or new.driver_id         is distinct from old.driver_id
    or new.route_id          is distinct from old.route_id
    or new.cargo_description is distinct from old.cargo_description
    or new.origin            is distinct from old.origin
    or new.destination       is distinct from old.destination
    or new.created_at        is distinct from old.created_at then
      raise exception
        'Drivers may only update status, location and waypoint fields';
    end if;
  end if;
  return new;
end;
$$;

create trigger trg_shipments_driver_scope
  before update on public.shipments
  for each row execute function public.enforce_driver_update_scope();
```

### 10.5 Route closure → automatic alerts (PRD §22–§24)

The centrepiece of the live demo. One admin `UPDATE` produces alerts, status changes and
timeline entries atomically.

```sql
create or replace function public.on_route_status_change()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
declare
  affected record;
  msg text;
  sev public.alert_severity;
begin
  if new.status is not distinct from old.status then
    return new;
  end if;

  if new.status = 'CLOSED' then
    msg := new.name ||
      ' လမ်းကြောင်း ပိတ်ထားပါသည်။ သင်၏ကုန်ပစ္စည်း ပို့ဆောင်မှု နောက်ကျနိုင်ပါသည်။';
    sev := 'HIGH';
  else
    msg := new.name || ' လမ်းကြောင်း ပြန်လည်ဖွင့်လှစ်ပါပြီ။';
    sev := 'NORMAL';
  end if;

  for affected in
    select id, trader_id, driver_id, status
    from public.shipments
    where route_id = new.id
      and status <> 'DELIVERED'
  loop
    -- Alert the trader
    insert into public.alerts (route_id, shipment_id, recipient_id, message, severity)
    values (new.id, affected.id, affected.trader_id, msg, sev);

    -- Alert the assigned driver, if any
    if affected.driver_id is not null then
      insert into public.alerts (route_id, shipment_id, recipient_id, message, severity)
      values (new.id, affected.id, affected.driver_id, msg, sev);
    end if;

    -- A closure delays shipments that are already under way
    if new.status = 'CLOSED'
       and affected.status in ('PICKED_UP', 'IN_TRANSIT', 'CHECKPOINT', 'CUSTOMS') then

      update public.shipments
         set status = 'DELAYED'
       where id = affected.id;

      insert into public.shipment_events (shipment_id, status, description)
      values (affected.id, 'DELAYED', 'Route closed: ' || new.name);
    end if;
  end loop;

  return new;
end;
$$;

create trigger trg_route_status_change
  after update of status on public.routes
  for each row execute function public.on_route_status_change();
```

Reopening a route sends a `NORMAL` alert but does **not** automatically move shipments
back to `IN_TRANSIT` — the driver does that, which keeps the timeline honest and matches
the demo script in PRD §56.

## 11. Realtime Configuration

Realtime is opt-in per table. Without these statements the subscriptions connect
successfully and then silently deliver nothing — a failure mode that costs hours.

```sql
alter publication supabase_realtime add table public.shipments;
alter publication supabase_realtime add table public.shipment_events;
alter publication supabase_realtime add table public.alerts;
alter publication supabase_realtime add table public.routes;

-- Required so Realtime can evaluate RLS against the full old/new row.
alter table public.shipments       replica identity full;
alter table public.alerts          replica identity full;
alter table public.routes          replica identity full;
alter table public.shipment_events replica identity full;
```

Client subscription pattern:

```ts
const channel = supabase
  .channel(`shipment:${shipmentId}`)
  .on('postgres_changes',
      { event: 'UPDATE', schema: 'public', table: 'shipments',
        filter: `id=eq.${shipmentId}` },
      (payload) => setShipment(payload.new as Shipment))
  .subscribe();

return () => { supabase.removeChannel(channel); };  // always unsubscribe
```

Realtime re-applies RLS per subscriber, so a trader's channel cannot receive another
trader's rows even if the filter is wrong.

## 12. Storage

```sql
insert into storage.buckets (id, name, public)
values ('shipment-documents', 'shipment-documents', false);

-- Path convention: shipment-documents/<shipment_id>/<uuid>-<filename>
create policy "documents_upload_assigned_driver"
  on storage.objects for insert to authenticated
  with check (
    bucket_id = 'shipment-documents'
    and exists (
      select 1 from public.shipments s
      where s.id::text = (storage.foldername(name))[1]
        and s.driver_id = auth.uid()
    )
  );

create policy "documents_read_participants"
  on storage.objects for select to authenticated
  using (
    bucket_id = 'shipment-documents'
    and exists (
      select 1 from public.shipments s
      where s.id::text = (storage.foldername(name))[1]
    )
  );
```

The bucket is private; the UI reads files through short-lived signed URLs
(`createSignedUrl`). Storage policies are separate from table RLS — securing
`public.documents` does not secure the files themselves.

## 14. Frontend Notes That Affect the Architecture

### 14.1 Leaflet must not render on the server

Leaflet touches `window` at import time, so a plain import breaks the Vercel build.

```ts
// components/map/TrackingMapLoader.tsx
const TrackingMap = dynamic(() => import('./TrackingMap'), {
  ssr: false,
  loading: () => <div className="h-96 animate-pulse bg-slate-100" />,
});
```

The default marker icons also fail to resolve under a bundler; set `L.Icon.Default`
`iconUrl`/`shadowUrl` explicitly, or use a `divIcon` with a Lucide truck glyph.

### 14.2 Server vs client components

Server components fetch initial data (fast first paint, no loading spinner). Any component
that subscribes to Realtime, renders the map, holds form state, or reads `localStorage`
must be `'use client'`. This boundary is where AI-generated Next.js code fails most often —
the usual symptom is a `useState`/`useEffect` in a server component.

### 14.3 Cookie-based sessions

Use `@supabase/ssr` (`createBrowserClient`, `createServerClient`), not the deprecated
`@supabase/auth-helpers-nextjs` that most models still suggest. The middleware must refresh
the session cookie on every request or server components will intermittently see a logged-out user.

## 15. Risks and Verification Checklist

| Risk | Mitigation | Verify in |
|---|---|---|
| RLS policy recursion via `profiles` | `SECURITY DEFINER` helpers (§8.2) | Phase 4 |
| Realtime silently delivers nothing | Publication + replica identity (§11) | Phase 8, with two browsers |
| Leaflet breaks the production build | `dynamic(..., { ssr: false })` | Phase 7, run `npm run build` locally |
| Offline sync duplicates events | Client UUID + `on conflict do nothing` | Phase 10, sync twice deliberately |
| Route closure alerts only some users | Database trigger, not a client loop | Phase 9 |
| Demo data unrecoverable after a bad run | `reset_demo()` function | Phase 13 |
| Env vars missing on Vercel | Set in dashboard, not only `.env.local` | Phase 13 |

### Build order

Dependency order, not PRD numbering:

```text
Schema + RLS → Auth + role routing → Driver write path → Realtime read path
  → Map → Route-closure trigger → Offline queue → Documents
```

Everything after "Realtime read path" is independently demoable, so if time runs short the
cut comes from the right-hand end without breaking what precedes it.

### Manual RBAC test matrix

Run with three browser profiles signed in simultaneously:

- [ ] Trader B cannot read Trader A's shipment by ID or by URL
- [ ] Driver cannot `UPDATE public.routes` (expect a policy violation, not a hidden button)
- [ ] Driver cannot reassign `driver_id` on their own shipment (expect the §10.4 exception)
- [ ] Trader cannot change `shipments.status`
- [ ] Non-admin cannot set their own `role` to `ADMIN` (expect the §10.3 exception)
- [ ] Trader receives the alert on closure; an unaffected trader does not
- [ ] Location change reaches admin and trader views with no refresh
- [ ] Offline update survives a page reload and syncs exactly once
